# Lessons

- ユーザーから「テストが必須」と明示されたら、unit test だけで終えず、要求された検証レベルまで自動テストを追加してから完了扱いにする。
- canvas / animation 系の変更では、状態遷移の unit test と実ブラウザ smoke test を最初から計画に入れる。
- ファイル移設が目的の変更では、内容変更を混ぜない。移設後に元ファイルとの差分を確認し、実質 rename になっていることを確認してから完了扱いにする。
- コンテンツ構造や scene 切り替え単位は、実装都合で細かく分解しない。記事単位・ページ遷移単位など、ユーザーが指定した編集モデルを source of truth にする。
- animation / shader の time は「何を起点に進むべきか」を先に固定する。runtime 単位の都合で clock semantics を決めず、ユーザーが指定した基準時間を controller と debug 名に反映する。
- レイアウト変更で canvas の表示サイズを動かすときは、`ResizeObserver` を足すだけで終わらせず、`resize()` 後に可視 canvas が即再描画されるか確認する。`canvas.width` / `canvas.height` の更新は内容を消す前提で扱う。
- ユーザーが「最小変更」と明示したら、既存ロジックの分岐点を直接上書きする案から先に検討する。設定層や新しい抽象化を足す前に、今ある判定値を強制できるか確認する。
- ユーザーが「このファイルに分けないで」と修正したら、共有 helper の切り出しを既成事実化しない。まず元コンポーネント内へ戻し、テスト側で必要な補助計算もローカルに閉じる。
- ユーザーが「もっときれいにまとまる」と構造修正したら、`slot` で包んだだけの共有化で止めない。呼び出し側テンプレートの重複量を見て、props と配列駆動に寄せて呼び出し側を先に薄くする。
- ユーザーがテンプレート整理だけを求めているときは、`v-for` によるデータ駆動化まで自動で進めない。件数が固定なら、呼び出し側は明示的に並べたまま共通コンポーネント化だけで止める。
